근력 운동의 반복 수는 자료의 활동 조건이며 추천 반복 수가 아니다. 종목별 세트·중량·개별 운동 자세별 MET를 임의로 만들지 않는다. 긴 휴식·대기·다른 종목이 섞인 전체 시간에 같은 MET를 적용할 경우 오차가 커질 수 있어 활동 조건을 구분하도록 안내한다. UI의 종목 선택은 분류별로 묶었으며, 서버는 단일 운동 목록에서 지원 코드를 검증해 목록과 입력 허용 코드가 어긋나지 않게 했다.

## 계산과 해석

공식 사이트의 1 MET ≈ 1 kcal/kg/hour 정의를 사용한 근사식:

- 운동 중 총 소모량(kcal) ≈ MET × 운동 당시 체중(kg) × 분 / 60
- 안정 시 소모량 제외(kcal) ≈ (MET − 1) × 체중 × 분 / 60

가상 예: 2.8 MET, 70kg, 30분 → 총 98kcal, 안정 시 제외 63kcal. 표준 MET는 개인 실측값이 아니며 체력·동작·환경·대사 차이를 반영한 보정 모델을 구현하지 않았다. 두 값 중 어느 것도 유지 에너지에 자동 가산하거나 식사 열량에서 차감하지 않는다. 음식별 필수 보상 운동량이나 정확한 체중 감소로 해석하지 않는다.

운동 당시 나이·체중은 입력 스냅샷이다. 현재 프로필 값을 기본값으로만 제공하며 과거 날짜는 당시 값으로 바꿔야 한다. 입력 제한 0~300분·25~350kg은 제품 입력 범위이며 권장 운동량이 아니다. 0분은 0kcal이며 미기록과 구분한다. 미래 날짜·음수·비정상 숫자·미지원 코드는 거절한다.

## API·저장

- `GET /activities`: 지원 코드·조건·MET·출처.
- `POST /activities/calculate`: 계산만 수행하고 저장하지 않는다. 건강 정보 응답 캐시 금지, 요청 크기 제한·입력 비노출 오류 처리 적용.
- 화면에서 계산 후 ‘운동 기록에 추가’를 눌러 저장한다. 입력을 바꾸면 이전 계산 결과를 숨긴다. 날짜별 조회와 확인 후 삭제를 제공한다.
- 로그인 기록은 기존 소유권·CSRF·리비전 검사 경로로 `profiles.activity_records` JSONB에 저장한다. 서버가 계산을 다시 수행해 위조된 합계를 무시한다.
- 미변경 기록은 당시 MET·체중·시간·출처·계산 결과를 보존한다. 현재 프로필을 바꿔도 과거 기록을 재계산하지 않는다.
- 운동 필드를 모르는 이전 클라이언트 저장은 기존 운동 이력을 보존한다. 명시적인 빈 배열은 전체 삭제 의사로 기존 저장 경로에서 처리한다.
- `002_activity_records.sql`은 기존 기록을 보존하는 추가 컬럼 마이그레이션이며 개발·테스트 DB에 적용했다.
- 비로그인 기록은 로컬 임시 모드와 기존 브라우저 보관 선택을 따른다. 개인 운동 기록·DB·환경 파일은 Git에 올리지 않는다.

- 프런트엔드 TypeScript·Vite 빌드 통과.
- 브라우저 전체 **19개 통과(29.2초)**: 계산·입력 변경 시 이전 결과 숨김·0분·로컬 보관·삭제 취소/확정·DB 새로고침 포함. 390px 운동 기록 화면 캡처도 직접 확인했다.
- 최초 전체 검사에서 기존 메뉴의 모바일 전환 직후 넘침 검사가 일시 실패했다. 별도 확인에서 너비 390px·문서 너비 390px를 확인했고, 반응형 차트가 재배치될 때까지 실제 너비 조건을 재확인하도록 검사 방식을 조정한 뒤 전체 검사를 통과했다.
- 브라우저 보관 안내에 운동 기록도 포함됨을 명시했다. 실제 건강정보나 인증키를 출력·업로드하지 않았다.
