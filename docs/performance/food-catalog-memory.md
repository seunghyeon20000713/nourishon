# 식품 조회 메모리 개선 · 2026-11-09

## 바꾼 이유와 방식

기존 API는 전체 식품 JSON을 한꺼번에 읽어 Python 객체, 정규화한 이름 목록, 코드별 사전을 보관했다. 작은 서버에서 시험하기 위해 식품 조회의 메모리 사용을 줄였다. 개인 계정·건강 기록의 PostgreSQL 저장 방식은 그대로다.

`backend/food_catalog.py`는 Python 표준 라이브러리만 사용한다. 서버 시작 시 완료된 `foods.json`을 65,536자씩 읽고 한 식품씩 임시 SQLite 조회 파일에 넣는다. 데이터 전체를 Python 목록으로 만들지 않는다. 중복 코드·100g 외 기준량·보고서와 다른 개수·잘린 JSON·잘못된 배열이면 시작을 거부하고 임시 파일을 정리한다. 원본 JSON과 보고서는 수정하지 않는다.

조회 파일은 OS 임시 디렉터리의 전용 폴더에 만들며 정상 종료 시 지운다. 재시작하면 다시 만든다. 개인 기록을 담지 않으며 Git에 올리지 않는다. 강제 종료 시 임시 파일이 남을 수 있어 배포 환경의 임시 저장소 정리 정책이 필요하다. 이번 전체 데이터에서 파일 크기는 **176.78MiB**였다. 원본 외에 쓰기 가능한 임시 디스크 공간이 필요하다. 호스팅이 임시 디스크를 RAM으로 제공한다면 프로세스 RSS 외의 비용도 별도로 확인해야 한다.

검색은 기존 NFKC·대소문자·공백 정규화를 거친 이름에 SQLite `instr`로 부분 일치한다. `%`와 `_`를 SQL 와일드카드로 바꾸지 않는다. SQL 값은 바인딩한다. 검색은 원본 순서를 유지한다. 비교는 해당 검색 결과만 순서대로 읽고 기존 Python 성분 비교 함수를 재사용한다. 동점·결측 뒤 배치·단위·출처·원본 행 번호가 유지된다. 섭취량 계산도 기존 함수를 사용하며 최대 100개 요청 항목에 필요한 식품만 읽는다.

요청마다 별도 읽기 전용 SQLite 연결을 사용하고 캐시는 연결당 약 2MiB로 제한한다. 테스트용 `rows=` 주입은 기존 메모리 카탈로그를 사용한다. 기존 카탈로그는 동등성 비교의 기준으로도 남겨두었다. API 주소·응답 구조·개인정보 DB·프런트엔드는 바꾸지 않았다.

## 같은 정제본으로 새 프로세스에서 비교

식품 **290,871개** 전체를 사용했다. 각 방식을 새 Python 프로세스에서 실행했다. 메모리는 Linux `/proc/self/status`의 RSS와 `resource.ru_maxrss`를 MiB로 환산했다. [측정값·결과 해시](food-catalog-benchmark.json)에 입력 파일 해시와 비교 결과를 보관한다. 실제 식품 행이나 개인정보는 들어 있지 않다.

| 항목 | 기존 메모리 목록 | 파일 조회 |
| --- | ---: | ---: |
| 시작 후 RSS | 514.26MiB | 58.61MiB |
| 44개 비교 후 RSS | 517.30MiB | 85.33MiB |
| 해당 프로세스 최대 RSS | 702.07MiB | 85.60MiB |
| 카탈로그 준비 | 1.426초 | 3.932초 |
| 준비 + 44개 작업 | 2.313초 | 7.316초 |

시작 후 RSS는 약 **88.6% 감소**했다. 위 값은 API 모듈을 불러온 카탈로그 측정 프로세스의 값이다. 실제 Uvicorn 서버의 메모리와 동일하다고 가정하지 않는다. 단일 실행이므로 평균·최댓값 보장·서로 다른 서버의 성능으로 일반화하지 않는다. 메모리를 줄이는 대신 시작·조회 시간이 늘었다.

44개 비교는 검색 16개, 성분 비교 27개, 한 끼 계산 1개다. 두부·현미밥·닭가슴살·사과·넓은 검색어·없는 검색어·리터럴 `%`·전각 영문 검색, 비교의 세 성분과 0/8/10000 오프셋을 포함한다. 계산은 0g·150g·37.5g과 중복 식품을 포함한다. 전체 응답을 정렬된 JSON으로 직렬화한 SHA-256을 비교했으며 **44개 모두 일치**했다. 전체 데이터의 가능한 모든 입력을 증명한 것은 아니다.

## 실제 API·브라우저 검증

기존 로컬 API를 정상 종료하고 새 방식으로 8000 포트에 다시 실행했다. PostgreSQL과 저장 기록은 유지했다.

- 백엔드 전체 **117개 통과(1.855초)**. 새 가상 데이터 검증 5개는 검색·비교·계산 동등성, 동시 읽기, 잘못된 데이터 거부·정리, JSON 청크 경계, 파일 기반 API 경로·종료 정리를 검사한다.
- 실제 새 API를 통한 관련 브라우저 **12개 통과(20.9초)**. 가입·재로그인·DB 기록, 음식 비교→150g 계산→기록, 검색·페이지·결측·0·오류·모바일 포함.
- 일반 두부 검색 한 번은 0.134초였다. 가장 깊은 허용 오프셋 10000에서 20개씩 반환하는 비교 네 요청을 동시에 보냈다. 같은 검색 결과 17,226개에서 모두 정상 응답했고 각각 2.116/2.058/2.091/2.049초였다. 이후 실제 API 프로세스의 관측 최대 RSS는 **213.11MiB**였다. 시작 직후 측정값과 다르며 Python 할당자가 메모리를 보관할 수 있다.

이번 검증은 제한된 로컬 실행이다. 512MB 클라우드에서의 메모리 한도 준수나 동시 사용자 수를 보장하지 않는다. 더 많은 동시 요청, 디스크·페이지 캐시, 계정 기록 크기, 플랫폼 오버헤드는 외부 테스트에서 따로 확인해야 한다. 외부 계정·서버·DB는 생성하지 않았고 공개 Sites 체험판도 변경하지 않았다.

## 재현

정제본이 로컬에 있는 상태에서 각각 별도 명령으로 실행한다.

```bash
.venv/bin/python -B scripts/benchmark-food-catalog.py --mode memory
.venv/bin/python -B scripts/benchmark-food-catalog.py --mode disk
```

전체 응답 대신 결과 해시·소요 시간·메모리만 출력한다. 실제 수집 데이터와 인증키를 커밋할 필요가 없다. 다음 단계는 선택한 외부 테스트 환경에서 저장 공간·HTTPS·별도 DB를 준비하고 같은 API 흐름을 검증하는 것이다.
