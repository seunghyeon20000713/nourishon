## 1. 결측값과 0을 구분하는 영양 계산·기간 평균 (소급 작성)

근거 문서: [meal-calculation.md](meal-calculation.md), [period-analysis.md](period-analysis.md), [nutrition-calculation.md](nutrition-calculation.md)

**문제 상황**
공공 식품 데이터는 성분값이 비어 있는 경우가 많다. 빈 값을 0으로 채우면 "나트륨 0mg"처럼 사실과 다른 정보가 된다. 기록하지 않은 날을 평균에 넣으면 섭취량이 실제보다 낮아 보인다.

**선택한 방법과 이유**
- 계산식은 `100g당 성분 × 섭취량(g) ÷ 100`. 100mL 등 다른 기준량은 밀도 정보 없이 g로 바꾸지 않고 별도로 보존했다.
- 한 끼 합계: 값이 있는 항목만 더하고 "누락 N개"를 표시한다. 전부 없으면 합계를 `None`("정보 없음")으로 둔다. 상태를 `complete / partial / missing`으로 구분한다.
- 기간 평균: 0 kcal로 기록한 날은 실제 값이므로 분모에 넣는다. 기록하지 않은 날과 성분이 전부 없는 날은 분모에서 뺀다. 분모가 며칠인지 화면에 표시한다.
- 이유: 영양사로서 "모른다"와 "없다"는 다르게 다뤄야 한다. 잘못된 0은 잘못된 식사 조언으로 이어진다.

**고려한 대안**
- 결측을 0으로 채우기: 구현은 쉽지만 결측이 많은 성분이 체계적으로 낮게 나온다.
- 결측을 평균값으로 채우기(대체): 통계적으로 쓰이지만 개인 기록에 추정값을 섞으면 사용자가 실제 값으로 오해한다.

**검증 방법과 결과 (로컬)**
- 가상 식품으로 일부·전체 결측과 0 구분, 0g 입력, 같은 식품 반복을 단위 테스트했다.
- 실제 표본 2개 식품의 7개 성분을 Decimal로 따로 계산해 대조했고, 차이는 0.000000001 미만이었다.
- 기간 분석 테스트를 쓰면서 처음 적은 기대값이 내 규칙과 어긋난 것을 발견했다. 0 kcal 기록일도 분모에 넣는 기준에 맞게 기대값을 500/3=166.67로 바로잡았다. 관련 브라우저 시나리오 10개 통과(13.0초).

**예상 질문과 답변**
- Q. 결측이 많으면 합계가 의미가 없지 않나요?
  A. 그래서 합계만 보여주지 않고 "누락 N개"와 `partial` 상태를 함께 보여줍니다. 누락이 있으면 주간 안내도 평가를 보류합니다. 숫자를 숨기는 것보다 신뢰 범위를 같이 보여주는 쪽을 택했습니다.
- Q. 0 kcal 기록을 왜 평균에 넣나요?
  A. 사용자가 "0"이라고 입력한 것은 정보입니다(예: 단식한 날). 기록하지 않은 날은 정보가 없는 것이라 뺍니다. 둘을 구분하지 않으면 평균이 실제보다 낮아집니다.

## 2. 화면과 API를 한 주소에서 제공 + `__Host-` 보안 쿠키 (소급 작성)

근거 문서: [deployment/staging-preparation.md](deployment/staging-preparation.md), [deployment/render-test-environment.md](deployment/render-test-environment.md)

**문제 상황**
개발 중에는 화면(Vite 5173)과 API(8000)가 서로 다른 주소다. 그대로 배포하면 브라우저가 다른 출처(origin)로 로그인 쿠키를 보내야 해서 CORS 설정과 쿠키 정책이 복잡해지고, 설정 실수가 곧 보안 구멍이 된다.

**선택한 방법과 이유**
- 외부 테스트용 앱은 React 빌드 결과를 `/`, 기존 API를 `/api/`로 한 서버(`backend.web:create_web_app`)에서 제공한다. 같은 출처라서 쿠키를 다른 사이트로 보낼 필요가 없다.
- 쿠키는 `__Host-` 접두사 + Secure·HttpOnly·SameSite=Strict·Path=/ 로 설정하고 Domain은 지정하지 않는다. 브라우저가 "HTTPS에서, 이 정확한 호스트에서만" 쿠키를 받도록 강제한다.
- 허용 Origin은 정확한 HTTPS 주소만 받는다. HTTP·localhost·와일드카드는 거절한다. 설정이 빠지면 서버가 시작을 거부하고, 로컬 개발 설정으로 몰래 대체하지 않는다.
- 정적 파일은 빌드 결과물만 제공하고 `.env`, `.git`, 식품 JSON, 백엔드 소스 경로는 차단한다.

**고려한 대안**
- 화면과 API를 다른 도메인에 두고 CORS + SameSite=None 쿠키: 흔한 방식이지만 CSRF(다른 사이트를 통한 요청 위조) 방어를 더 신경 써야 하고 설정 항목이 늘어난다.
- 토큰을 localStorage에 저장: 구현은 쉽지만 XSS(스크립트 주입)가 생기면 토큰이 그대로 빠져나간다. HttpOnly 쿠키는 스크립트가 읽을 수 없다.

**검증 방법과 결과 (로컬, 가상 HTTPS 주소)**
- 설정 누락·HTTP/localhost/와일드카드 Origin 거절, DB SSL 요구, 오류 메시지에 비밀값이 나오지 않는지, 잘못된 Host/Origin 차단, 정적 경로 차단을 테스트했다.
- 단일 주소 구성으로 브라우저 시나리오 12개 통과(14.4초): 가입·재로그인·DB 기록·음식 비교·섭취량 계산·모바일.
- 한계: 가상 HTTPS 주소의 쿠키 검사는 헤더·세션 동작 검사다. 실제 인증서 통신은 클라우드 배포 후 확인해야 한다.

**예상 질문과 답변**
- Q. `__Host-` 접두사는 뭘 막아 주나요?
  A. 브라우저가 Secure이고 Path=/이며 Domain이 없는 쿠키만 이 이름으로 저장하게 합니다. 그래서 하위 도메인이나 HTTP 페이지가 같은 이름의 쿠키를 덮어써 세션을 바꿔치기하는 공격을 막습니다.
- Q. SameSite=Strict만으로 CSRF가 다 막히나요?
  A. 대부분 막히지만, 저는 상태를 바꾸는 요청에 CSRF 토큰 헤더와 Origin 검사도 함께 둡니다. 브라우저 정책 하나에만 의존하지 않으려는 겹겹이 방어입니다.

## 3. 식품 조회 메모리 개선 — 전체 목록 → 파일 기반 SQLite 조회 (소급 작성)

근거 문서: [performance/food-catalog-memory.md](performance/food-catalog-memory.md)

**문제 상황**
식품 290,871개를 서버 시작 때 Python 목록으로 전부 메모리에 올렸다. API 프로세스 RSS(실제 사용 메모리)가 약 537MiB로 측정돼, 무료 서버 한도 512MB를 이미 넘었다.

**선택한 방법과 이유**
- 시작할 때 `foods.json`을 65,536자씩 나눠 읽어(스트리밍) 한 식품씩 임시 SQLite 파일에 넣는다. 데이터 전체를 메모리에 만들지 않는다.
- 검색·비교·계산은 필요한 행만 SQLite에서 읽는다. 기존에 테스트된 Python 계산 함수는 그대로 재사용해서 결과가 바뀌지 않게 했다.
- 표준 라이브러리만 사용해 의존성을 늘리지 않았다. 검색어는 바인딩하고 `%`, `_`를 와일드카드로 해석하지 않는다.
- 중복 코드·100g 외 기준량·개수 불일치·잘린 JSON이면 시작을 거부하고 임시 파일을 정리한다.

**고려한 대안**
- 식품 데이터를 PostgreSQL에 넣기: 메모리는 줄지만 무료 DB 용량(Neon/Render 무료 한도)을 식품 데이터가 차지하고, 개인 기록 DB와 공공 데이터가 섞인다.
- 더 큰 유료 서버: 코드 변경 없이 해결되지만 비용이 든다. 무료 원칙에 맞지 않는다.
- 외부 검색 엔진(Elasticsearch 등): 이 규모에는 과하고 운영 비용이 든다.

**검증 방법과 결과 (로컬, 각 방식을 새 프로세스에서 1회 측정)**

| 항목 | 기존 메모리 목록 | 파일 조회 |
| --- | ---: | ---: |
| 시작 후 RSS | 514.26MiB | 58.61MiB (약 88.6% 감소) |
| 해당 프로세스 최대 RSS | 702.07MiB | 85.60MiB |
| 카탈로그 준비 | 1.426초 | 3.932초 |

- 대가: 시작이 약 2.5초 느려지고, 임시 파일 176.78MiB만큼 디스크가 필요하다.
- 동등성: 검색 16·비교 27·계산 1, 총 44개 요청의 전체 응답을 SHA-256으로 비교해 **44개 모두 일치**했다.
- 실제 API에 동시 요청 4개를 보낸 뒤 관측한 최대 RSS는 213.11MiB였다.
- 한계: 로컬 단일 측정이다. 512MB 클라우드에서의 한도 준수와 동시 사용자 수는 배포 후 따로 확인해야 한다.

**예상 질문과 답변**
- Q. 왜 시작 시간이 늘어나는 걸 받아들였나요?
  A. 무료 서버는 메모리 한도를 넘으면 아예 실행되지 않지만, 시작 2.5초는 사용자가 견딜 수 있는 비용이라고 판단했습니다. 다만 무료 서버는 절전 후 다시 깨어날 때 이 시간이 첫 접속에 더해지므로 README에 안내합니다.
- Q. 결과가 같다는 건 어떻게 보장했나요?
  A. 기존 방식을 기준으로 남겨 두고, 경계 사례(없는 검색어, `%` 같은 특수문자, 전각 영문, 0g·소수 g, 깊은 페이지)를 포함한 44개 요청의 응답 전체를 해시로 비교했습니다. 모든 입력을 증명한 건 아니라는 한계도 문서에 적었습니다.

## 4. GitHub Actions CI — 일회용 PostgreSQL로 백엔드 테스트 전체 실행 (2026-11-16)

근거 문서: [ci.md](ci.md)

**문제 상황**
백엔드 테스트 118개 중 계정·세션·CSRF 테스트 12개는 PostgreSQL 테스트 DB가 있어야만 실행되고, 없으면 조용히 건너뛰었다. 로컬 기본 실행 결과가 `OK (skipped=12)`라서, 가장 중요한 보안 테스트가 빠진 채 "통과"로 보였다. 자동 테스트 장치(CI)도 없었다.

**선택한 방법과 이유**
- GitHub Actions에서 push·PR마다 PostgreSQL 16 서비스 컨테이너(테스트 동안만 존재하는 일회용 DB)를 띄워 118개를 전부 실행한다.
- 테스트는 소유자가 아니라 권한이 좁은 앱 역할(테이블 읽기·쓰기만)로 접속한다. 실제 서버와 같은 조건이다.
- 출력에 `skipped=`가 있으면 CI를 실패시킨다. unittest는 건너뜀이 있어도 성공으로 끝나기 때문이다.
- 권한 부여 코드를 `grant_app_role()` 함수로 분리해 로컬 설정과 CI가 같은 규칙을 쓴다.
- 비용 0원: 공개 저장소의 GitHub 기본 실행기는 무료다. 비밀값도 쓰지 않는다.

**고려한 대안**
- DB 테스트를 SQLite로 대체: 빠르지만 PostgreSQL 전용 문법(jsonb 등)과 권한 모델을 검증하지 못한다.
- 소유자 계정으로 테스트: 설정은 쉽지만 앱 역할의 권한 부족 문제를 놓친다.
- 건너뜀 허용: 설정 실수 하나로 보안 테스트가 조용히 빠진다.

**검증 방법과 결과 (로컬)**
- 로컬 테스트 DB에 앱 역할로 접속: 118개 통과, 건너뜀 0.
- CI 재현: 비밀번호 인증·TCP 접속을 켠 새 임시 PostgreSQL 16 서버에서 워크플로 단계를 그대로 실행. DB 준비 2회 연속 성공, 118개 통과, 건너뜀 0.
- 안전장치: DB 이름이 `nourishon_test`가 아니면 준비 스크립트가 멈춘다. 테스트 DB 설정을 빼면 건너뜀 12개가 감지된다.
- 첫 GitHub 실행에서 1개 실패: `backend/web.py`가 불러오는 순간 앱을 만들어 로컬에만 있는 `frontend/dist`를 요구했다. `uvicorn --factory`로 바꿔 해결했고, Git 파일만 있는 깨끗한 복사본에서 수정 전 실패·수정 후 127개 통과를 확인했다.

**예상 질문과 답변**
- Q. CI의 DB 비밀번호를 YAML에 그대로 적었는데 괜찮나요?
  A. 실행기 안에서만 접속할 수 있고 몇 분 뒤 사라지는 빈 DB라서 지킬 비밀이 없습니다. 실제 서버의 DB 연결 정보는 호스팅 서비스의 비밀 설정에만 넣고 Git에는 올리지 않습니다. 비밀이 있는 값과 없는 값을 구분해서 다룬 것입니다.
- Q. 테스트가 건너뛰어지는 걸 왜 실패로 처리했나요?
  A. 건너뛴 12개가 계정 분리·세션·CSRF 같은 보안 테스트였습니다. 초록 표시가 "검사하지 않았음"을 숨기면 안 된다고 봤습니다. 이후 챗봇이 "본인 기록만 조회"를 지키는지도 이 테스트들 위에서 검증할 계획입니다.
- Q. CI를 붙이고 실제로 잡은 문제가 있나요?
  A. 첫 실행에서 로컬에서는 통과하던 테스트가 실패했습니다. 웹 앱 모듈이 불러오는 순간 로컬에만 있던 화면 빌드 폴더를 요구했기 때문입니다. 앱 생성을 팩토리 함수 호출로 미뤄서 해결했습니다. "내 컴퓨터에서는 되는데"를 CI가 잡아낸 사례입니다.

## 5. 비공개 식품 데이터를 빌드 때 안전하게 받기 — Release + 세분화 토큰 + SHA-256 (2026-11-16)

근거 문서: [deployment/food-data-release.md](deployment/food-data-release.md)

**문제 상황**
식품 정제본은 Git에 올리지 않는다. 그래서 무료 Render가 빌드할 때 받을 곳이 없고, 무료 플랜에는 SSH도 없다.

**선택한 방법과 이유**
- 별도 비공개 GitHub 저장소의 Release에 압축본을 첨부하고, 그 저장소만 읽을 수 있는 만료일 있는 세분화 토큰으로 빌드 중에 내려받는다.
- 미리 기록한 SHA-256과 일치할 때만 배치한다. 파일이 바뀌거나 깨지면 빌드가 실패한다.
- GitHub이 돌려주는 서명된 다운로드 주소에는 토큰을 보내지 않는다. 서버 시작 직전에 토큰을 환경에서 지운다.
- 비용 0원, 새 서비스 가입 없음.

**고려한 대안**
- R2/S3 비공개 저장소: 업계 표준에 가깝지만 외부 계정과 결제 수단 등록 가능성이 있다.
- 빌드 때 공공 API 재수집: 느리고 호출 한도가 있으며, 검증한 데이터와 같다는 보장이 없다.

**검증 방법과 결과 (로컬)**
- 가짜 GitHub 서버로 테스트 9개 통과: 토큰 미전송, 해시 불일치 시 미배치, `../` 경로 거부, 실패 시 기존 데이터 유지, 오류 메시지에 비밀 미노출.
- 실제 정제본 149,361,969 bytes → 압축 11,149,575 bytes. 두 번 묶어 같은 SHA-256, 풀어서 원본과 일치.
- 실제 GitHub·Render 환경 다운로드는 아직 미실행.

**예상 질문과 답변**
- Q. 해시는 왜 확인하나요? HTTPS면 충분하지 않나요?
  A. HTTPS는 전송 중 변조를 막지만, Release에 잘못된 파일이 올라간 경우는 못 막습니다. 해시는 "내가 검증한 바로 그 파일"인지 확인합니다. 해시를 Render 설정에 고정해 두었기 때문에, 파일을 바꾸려면 해시도 같이 바꿔야 해서 실수로 데이터가 바뀌지 않습니다.
- Q. 토큰이 유출되면요?
  A. 그 비공개 저장소 하나의 읽기만 가능하고 만료일이 있습니다. 공공 데이터를 정제한 파일이라 개인정보는 없습니다. 실행 중인 서버에서는 환경변수를 지워 노출 면적을 줄였습니다.

## 6. 무료로 실제 서버 배포 — Render + Neon + 비공개 Release (2026-11-16)

근거 문서: [deployment/render-test-environment.md](deployment/render-test-environment.md)

**문제 상황**
로컬에서만 돌던 서비스를 비용 0원으로 외부에 공개해야 했다. 조건은 세 가지였다. 식품 원본은 공개 저장소에 올리지 않는다. DB는 포트폴리오 기간 동안 만료되면 안 된다. 비밀값은 채팅·Git에 남기지 않는다.

**선택한 방법과 이유**
- 웹 서버: Render 무료(싱가포르). 화면과 API를 한 주소로 제공하고, `/api/ready`가 식품·DB·스키마를 확인한 뒤에만 사용자를 연결한다.
- DB: Neon 무료. Render 무료 Postgres는 30일 뒤 만료되기 때문이다. 무료 플랜은 한도를 넘으면 과금 대신 정지한다.
- DB 계정 분리: 소유자 계정은 마이그레이션에만 한 번 쓰고 저장하지 않았다. 서버는 테이블 읽기·쓰기만 되는 앱 역할로 접속한다.
- 버전 차이: Neon이 PostgreSQL 18로 만들어졌는데, 로컬은 16이다. 준비 스크립트가 버전 불일치를 감지해 아무것도 바꾸지 않고 멈췄다. 이후 CI를 16·18 두 버전으로 늘려 둘 다 통과한 뒤에 적용했다.
- 비밀값: 연결 문자열은 화면에 보이지 않게 입력받았다. 앱 연결 정보와 GitHub 토큰은 Render 비밀 설정에만 넣었다.

**고려한 대안**
- AWS(EC2·RDS·S3): 취업 시장 키워드로는 유리하지만 카드 등록이 필요하고 과금 위험이 있어 무료 원칙에 맞지 않았다. 대신 대응 관계(RDS↔Neon, S3↔Release, Secrets Manager↔Render 비밀 설정)로 설명할 수 있게 정리할 예정이다.
- Render 무료 Postgres: 설정은 가장 간단하지만 30일 만료.

**검증 방법과 결과 (클라우드)**
- 외부에서 `/api/ready` 200, 식품 검색 "두부" 3,218건. 비밀·소스 경로 404, 위장 Host 403, 개인정보 응답 `no-store`.
- 배포 시작부터 준비 완료 확인까지 약 7분(빌드 포함). 절전 후 재시작 시간은 미측정.
- 가상 계정 브라우저 사용 흐름은 개발자가 직접 확인했다.

**예상 질문과 답변**
- Q. 왜 서버와 DB를 다른 회사에 두었나요?
  A. 비용 0원과 데이터 보존 기간을 둘 다 만족하는 조합이었습니다. 두 서비스를 같은 싱가포르 지역에 두어 지연을 줄였습니다. 서비스마다 역할을 하나씩만 맡겨서 장애 원인을 찾기도 쉽습니다.
- Q. 운영 DB 버전이 로컬과 다르면 위험하지 않나요?
  A. 그래서 준비 스크립트가 검증하지 않은 버전이면 아무것도 바꾸지 않고 멈추게 했습니다. CI에서 두 버전을 모두 통과시킨 뒤에만 적용했습니다. 추측 대신 테스트로 호환성을 확인한 것입니다.

## 7. 지인 공유 전 보완 — 실제 사용자 IP 제한, 테스트 서버 안내, 회원 탈퇴 (2026-11-16)

근거 문서: [deployment/render-test-environment.md](deployment/render-test-environment.md) "보완 ①②③"

**문제 상황**
배포한 뒤 지인에게 공유하기 전에 코드를 다시 읽다가 세 가지를 발견했다.
- 로그인 시도 제한이 프록시 IP를 기준으로 해서 모든 사용자가 한 묶음을 공유할 수 있었다.
- 화면에 "가상 정보만 입력" 안내가 없었다.
- 회원 탈퇴 기능이 없었다.

**선택한 방법과 이유**
- IP: Render 앞단 Cloudflare가 요청마다 덮어쓰는 `CF-Connecting-IP`를, 환경변수로 켰을 때만 믿는다. `X-Forwarded-For` 맨 앞 값은 사용자가 위조할 수 있어서 쓰지 않는다.
- 안내: 체험판의 안내 띠를 공통 함수로 분리하고, 빌드할 때 플래그를 주어 테스트 서버에서만 켠다.
- 탈퇴: 비밀번호를 다시 확인한 뒤 계정 행 하나를 지운다. 나머지 기록은 DB의 `ON DELETE CASCADE`가 한 트랜잭션에서 함께 지운다. 틀린 비밀번호도 로그인과 같은 시도 제한을 받는다.

**고려한 대안**
- uvicorn `--forwarded-allow-ips='*'`: 결국 위조 가능한 헤더를 믿게 된다.
- 30일 유예 삭제: 복구는 가능하지만, 삭제 요청에 바로 응하는 원칙에는 즉시 삭제가 더 맞다.

**검증 방법과 결과 (로컬)**
- IP: 같은 IP는 41번째에 429가 되지만 다른 IP는 통과한다. `X-Forwarded-For`를 위조해도 우회되지 않는다.
- 탈퇴: 내 기록 5개 표는 모두 0건이 되고, 다른 사용자 기록은 그대로다. 틀린 비밀번호·CSRF 없음·다른 Origin이면 아무것도 지워지지 않는다. 시도 제한도 확인했다.
- 백엔드 140개 통과. 브라우저 확인은 배포 후에 한다.

**예상 질문과 답변**
- Q. 탈퇴할 때 왜 비밀번호를 다시 받나요? 이미 로그인했잖아요.
  A. 공용 PC에 로그인이 남아 있거나 세션이 탈취된 경우에도 되돌릴 수 없는 작업은 막기 위해서입니다. 은행 이체나 비밀번호 변경처럼, 위험한 작업 직전에 본인을 다시 확인하는 일반적인 방식입니다.
- Q. 정말 다 지워졌는지 어떻게 확인했나요?
  A. 테스트에서 계정 하나에 신체·식사 기록을 저장한 뒤 탈퇴시키고, 관련 5개 표를 직접 조회해 0건인지 확인했습니다. 함께 만든 다른 계정의 건수는 바뀌지 않았다는 것도 확인했습니다. 다만 DB 서비스의 복구용 기록에는 최대 6시간 남는다는 한계를 화면에 적었습니다.

## 8. `null`과 `undefined` — 결측이 0으로 보이던 버그 (2026-11-17)

근거 문서: [design/redesign-2026-11/README.md](design/redesign-2026-11/README.md) "진행 기록"

**문제 상황**
화면 점검 캡처에서 체성분을 입력하지 않은 가상 계정의 대시보드가 골격근량 `0.0 kg`를 보여줬다. 서버는 빈 값을 `null`로 주는데, 화면은 `undefined`만 "미등록"으로 처리했다. 같은 데이터를 "기록 관리" 화면은 바르게 보여줘서 화면끼리 결과가 달랐다.

**선택한 방법과 이유**
- 결측 검사를 `== null`로 바꿨다. JavaScript에서 `== null`은 `undefined`와 `null`만 참이 되고, 0은 거짓이다. 그래서 "없음"과 "0"을 정확히 나눈다.
- 서버 저장 형식(`null`)은 바꾸지 않았다. 이미 저장된 기록에도 `null`이 있기 때문에, 서버만 고치면 기존 데이터는 계속 0.0으로 보인다.

**고려한 대안**
- 서버에서 `exclude_none`으로 빈 값을 아예 빼고 저장: 새 기록만 고쳐지고 기존 기록은 그대로다. 화면에서 두 경우를 모두 처리하는 쪽이 안전하다.
- `!value` 검사: 0도 거짓이라 실제 0 값을 결측으로 잘못 보여 준다. 영양 데이터에서 0은 유효한 값이다.

**검증 방법과 결과 (로컬)**
- null 체성분을 넣은 브라우저 테스트를 추가했다. 수정 전에는 실패하고 수정 후에는 통과한다.
- 브라우저 테스트 전체 27개 통과. 그 과정에서 날짜가 고정돼 시간이 지나며 깨지던 테스트 2개와, 어제 기능 추가로 깨진 테스트 1개도 고쳤다.

**예상 질문과 답변**
- Q. 왜 단위 테스트에서 못 잡았나요?
  A. 서버 테스트는 서버가 `null`을 돌려주는 것까지만 확인했고, 화면 테스트는 체성분 값이 모두 있는 데이터만 썼습니다. 서버와 화면 사이의 계약, 즉 "빈 값은 null"을 양쪽 테스트가 공유하지 않았던 것이 원인입니다. 그래서 실제 서버 응답 형식(null)을 화면 테스트 데이터에 넣었습니다.
- Q. 날짜에 의존하는 테스트는 어떻게 막나요?
  A. 테스트 데이터의 날짜를 고정할 때는 화면의 선택 날짜도 같이 고정하거나, 실제 오늘 날짜를 계산해 씁니다. 이번에 깨진 두 테스트가 그 예입니다.

## 9. 화면 점검과 개선안 A — "첫 화면에서 할 일이 보이게" (2026-11-17)

근거 문서: [design/redesign-2026-11/README.md](design/redesign-2026-11/README.md)

**문제 상황**
기능은 많아졌지만 처음 온 사용자가 무엇부터 할지 알기 어려웠다. 시작 단계가 첫 화면 아래에 있었고, 메뉴 버튼이 중복됐고, 모바일 첫 화면의 약 38%를 안내와 헤더가 차지했다. 서버가 잠들어 연결이 안 되면 그냥 빈 화면처럼 보였다.

**선택한 방법과 이유**
- 먼저 측정했다. 테스트 DB와 가상 계정으로 데스크톱·모바일 주요 화면 20장을 찍고, 문제를 정확성(P0) → 첫 화면·일관성(P1) → 읽기 편함(P2) 순으로 정리했다.
- 개선안 3가지(정리형·카드형·강조색)를 코드 변경 없이 CSS 미리보기로 비교하고 개발자가 고르게 했다. 위험이 낮은 A를 먼저, 그 위에 B를 얹는 순서다.
- 위치는 눈대중 대신 브라우저에서 요소 좌표를 재서 맞췄다(데스크톱 버튼 세로 중앙 98px 통일).

**고려한 대안**
- 처음부터 전면 리디자인(B·C): 볼거리는 크지만 신뢰 문제(P0)와 동시에 바꾸면 무엇이 무엇을 깨뜨렸는지 구분하기 어렵다.
- 시작 단계를 팝업으로 띄우기: 눈에는 띄지만 닫으면 다시 찾기 어렵다. 대시보드 맨 위에 두고, 다 마치면 아래로 접히게 했다.

**검증 방법과 결과 (로컬)**
- 브라우저 테스트 29개 통과(서버 연결 실패 안내 2개 추가).
- 전/후 캡처를 docs에 남겼다. 모바일 제목 시작 위치가 약 300px에서 약 150px로 올라왔다(캡처 기준).
- 내 실수 2개(고정 상단 바가 계정 버튼을 덮음, CSS 선택자 우선순위로 여백 무시)를 캡처 자동화와 실측으로 찾아 고쳤다.

**예상 질문과 답변**
- Q. 디자인 결정을 어떻게 했나요? 감으로 했나요?
  A. 먼저 화면을 상태별로 캡처해 문제를 우선순위로 정리했고, 고칠 때는 요소 좌표를 재서 정렬을 맞췄습니다. 글자 대비도 WCAG 공식으로 계산했습니다(2.88:1 → 5.19:1).
- Q. UI를 바꾸면서 테스트가 깨졌을 때 어떻게 했나요?
  A. 의도한 변경 때문에 깨진 것인지, 원래 있던 문제인지부터 나눴습니다. 그 과정에서 "화면이 그려지기 전에 메뉴 버튼이 보이는지 판단하던" 경쟁 상태를 찾았고, 공통 도우미가 기다린 뒤 판단하도록 고쳤습니다.

## 10. 운동 목록을 쉬운 말로 — 공식 이름은 지키고 화면만 번역 (2026-11-17)

**문제 상황**
운동 선택이 25개 항목의 긴 드롭다운 하나였고, 항목 이름에 mph·W·MET 같은 전문 표현이 섞여 있었다. 개발자 본인도 "일반인이 보기에 너무 어렵다"고 판단했다.

**선택한 방법과 이유**
- 서버의 공식 Compendium 이름·MET·계산식은 그대로 두고, 프론트에 코드별 **화면용 번역표**(`activityGuide.ts`)를 두었다. 출처의 정확성(계산·저장)과 읽기 쉬움(화면)을 층으로 나눈 것이다.
- 선택을 3단계(종류 → 세부 조건 → 시간)로 나누어 한 번에 보는 항목을 25개에서 최대 6개로 줄였다.
- 강도는 공식 MET 구분(3 미만/3~6 미만/6 이상)으로만 표시해, 서비스가 임의 기준을 만들지 않게 했다.

**고려한 대안**
- 백엔드 이름 자체를 바꾸기: 이미 저장된 기록의 이름과 새 기록이 달라지고, 공식 명칭 추적이 어려워진다.
- 검색창으로 고르기: 25개뿐이라 검색보다 눈으로 고르는 편이 빠르고, 비슷한 이름을 잘못 고를 위험이 크다.

**검증 방법과 결과 (로컬)**
- 브라우저 테스트 32개 통과. 분류 7개·러닝 4개·근력 6개, 화면에 `mph`가 없음, 쉬운 이름·강도 표시를 테스트로 확인했다.
- 계산값(98·140·297.5 kcal 등)은 기존 테스트 기댓값 그대로 통과 → 표시만 바뀌고 계산은 같다.
- 전/후 캡처: `docs/design/redesign-2026-11/after-A/desktop-09-exercise.png` → `after-B/desktop-ex-records.png`.

**예상 질문과 답변**
- Q. 쉬운 말로 바꾸면 정확성이 떨어지지 않나요?
  A. 계산과 저장은 공식 코드·MET를 그대로 쓰고, 번역은 화면에만 적용했습니다. 기록 카드의 "자세히"에서 공식 이름·코드·버전·출처를 확인할 수 있습니다.
- Q. 왜 강도 색을 넣었나요?
  A. 사용자가 비슷한 이름 사이에서 고를 때 차이를 바로 보게 하려는 것입니다. 기준은 공식 MET 구분이고, 추천이 아니라 분류라는 점을 계산 방법 안내에 적었습니다.

## 11. 개선안 B — 디자인 토큰으로 화면 규칙 하나로 맞추기 (2026-11-17)

**문제 상황**
화면을 기능마다 따로 만들다 보니 색이 283종, 같은 이름의 색 변수(`--green`)가 파일마다 다른 값이었고, 8~11px 글자가 180곳, 입력칸 높이도 제각각이었다.

**선택한 방법과 이유**
- `tokens.css`에 색·모서리·그림자·글자 크기·조작 높이를 이름 붙여 모으고, `design-system.css`가 그 값으로 카드·버튼·입력칸을 덮어쓰게 했다. 기존 클래스 이름과 문구는 그대로 두어 테스트와 기능을 건드리지 않았다.
- 12px 미만 글자는 스크립트로 일괄 12px로 올렸다. 손으로 180곳을 고치면 빠뜨리기 쉽다.
- 체중 그래프 세로축은 1·2·5kg 단위의 반올림 눈금을 직접 계산해 넘겼다(P2-10).

**고려한 대안**
- CSS 프레임워크(Tailwind 등) 도입: 일관성은 좋지만 기존 1,900줄 CSS를 모두 옮겨야 해서 위험과 시간이 크다. 토큰 계층을 먼저 만들면 나중에 옮길 때도 값이 그대로 쓰인다.
- 기존 CSS 파일을 직접 고치기: 변경 위치가 흩어져 되돌리기 어렵다. 마지막에 불러오는 한 파일로 모아 변경 범위를 분명히 했다.

**검증 방법과 결과 (로컬)**
- 브라우저 테스트 32개 통과, 데스크톱·모바일 가로 넘침 없음.
- 세로축 테스트를 새로 추가하고, 이전 코드로 되돌리면 실패(눈금 70.1)하는 것을 확인했다.
- 전/후 캡처: `after-A/` → `after-B/`.

**예상 질문과 답변**
- Q. 디자인 토큰이 뭐고 왜 썼나요?
  A. 색·크기 같은 디자인 값을 이름 붙여 한 곳에 둔 것입니다. 화면마다 숫자를 직접 쓰면 비슷한 색이 수백 개로 늘어나는데, 이름으로 쓰면 한 곳만 바꿔 전체를 맞출 수 있습니다.
- Q. 그래프 눈금 수정은 어떻게 검증했나요?
  A. 눈금이 모두 정수 kg이고 3~6개인지 확인하는 테스트를 만들고, 일부러 이전 코드로 되돌려 실패하는 것을 본 뒤 새 코드로 통과시켰습니다. 테스트가 실제로 버그를 잡는지 확인한 것입니다.

## 12. "음식이 다 안 나와요" — 데이터가 아니라 검색 규칙 문제 (2026-11-17)

**문제 상황**
지인이 실제 서버에서 음식을 검색하면 일부가 안 나온다고 했다. DB 연결 문제처럼 보였지만, 서버 `/api/health`의 `food_count`는 290,871로 로컬과 같았다. 원인은 검색 규칙이었다. 원본 이름이 `김치찌개_돼지고기`처럼 붙여 쓰여 있어 `김치 찌개`는 0건이었고, 결과가 파일 순서(가공식품 95%)라 `바나나` 첫 결과가 도넛이었다.

**선택한 방법과 이유**
- 추측 대신 서버의 식품 개수부터 확인해 "데이터 누락"과 "검색 규칙"을 분리했다.
- 비교할 때만 공백·`_`·`,`·`·`를 무시하고, 여러 단어는 모두 포함된 이름을 찾는다. 원본 이름은 바꾸지 않는다.
- 순서는 같은 이름 → 검색어로 시작 → 포함, 같은 단계는 음식 → 원재료 → 가공식품 순이다.
- 실제 서버는 메모리를 아끼려고 SQLite 임시 파일 카탈로그를 쓴다. 두 구현(메모리·SQLite)이 같은 결과를 내는지 기존 비교 테스트로 묶었다. SQL은 단어 수만큼 `?`만 만들고 값은 바인딩한다.

**고려한 대안**
- 전문 검색 엔진(Elasticsearch 등): 형태소·오타 검색은 좋지만 무료 서버 메모리 512MB·비용 원칙에 맞지 않는다.
- 초성·동의어 검색: 범위가 커서 이번에는 띄어쓰기와 순서만 고쳤다.

**검증 방법과 결과 (로컬, 1회 측정)**
- 백엔드 테스트 144개 통과(DB 테스트 포함, 건너뜀 0). 띄어쓰기·여러 단어·순위·구분자만 있는 검색어 테스트 추가.
- `김치 찌개` 0건 → 410건, `그릭 요거트` 70건 → 644건, `바나나` 첫 결과 도넛 → 바나나. 응답 약 0.1초.
- 한계: `탄산음료_콜라`처럼 분류가 앞에 붙은 이름은 "검색어로 시작" 단계에 들지 않는다.

**예상 질문과 답변**
- Q. 사용자가 "검색이 안 된다"고 하면 어떻게 원인을 찾나요?
  A. 먼저 데이터가 다 있는지(서버의 식품 개수)와 검색 규칙을 나눠 봤습니다. 개수는 같았고, 같은 검색어를 로컬에서 재현해 띄어쓰기와 순서 문제를 찾았습니다.
- Q. 왜 순위를 넣었나요?
  A. 결과가 수천 건이어도 사용자는 첫 페이지만 봅니다. 데이터의 95%가 가공식품이라 파일 순서로는 원하는 음식이 묻혔습니다.

## 13. 같은 열량이 950과 949.7로 — 표시 규칙을 한 곳에 (2026-11-17)

**문제 상황**
대시보드 한 화면에서 같은 열량이 '오늘의 일기'에는 950 kcal, '기록된 열량'과 그래프에는 949.7 kcal로 보였다. 화면마다 반올림 코드를 따로 써서 생긴 문제다.

**선택한 방법과 이유**
- `nutrientFormat.ts` 한 곳에 단위별 규칙을 두었다: kcal·mg 정수, g·% 소수 첫째 자리(서비스 자체 규칙). 대시보드·식사 계산·기간 분석·음식 비교·운동 기록이 모두 이 함수를 쓴다.
- 계산·저장·평균은 원래 값으로 하고 보여줄 때만 반올림한다. 0이 아닌 작은 값이 0으로 보이면 기록된 0과 헷갈리므로 '0.1 미만'으로 표시한다(결측·0 구분 원칙).

**고려한 대안**
- 서버에서 반올림해 보내기: 합계·평균을 반올림된 값으로 다시 계산하면 오차가 쌓인다. 숫자는 정확히 두고 화면에서만 맞췄다.

**검증 방법과 결과 (로컬)**
- 규칙 함수 테스트와 "대시보드 두 곳이 같은 950"을 확인하는 브라우저 테스트 추가, 브라우저 테스트 34개 통과.
- 표시만 바뀐 기존 기대값 3개(297.5→298, 205.5→206, 166.67→167)는 계산값을 주석으로 남기고 고쳤다.

**예상 질문과 답변**
- Q. 반올림하면 정확도가 떨어지지 않나요?
  A. 계산과 평균은 원래 값으로 하고 화면만 반올림합니다. 예를 들어 평균은 500 ÷ 3 = 166.67로 계산하고 167로 보여줍니다.

## 14. 계산 결과가 안 보여요 — 결과로 이동 + 포커스 + 동작 줄이기 (2026-11-17)

**문제 상황**
지인 피드백: 식사 기록에서 '영양 합계 계산'을 눌러도 결과가 화면 아래에 생겨 계산이 된 줄 몰랐다. 화면 낭독기 사용자도 결과가 생긴 위치를 알기 어렵다.

**선택한 방법과 이유**
- 계산이 성공했을 때만 결과 제목으로 스크롤하고, 제목에 포커스를 옮긴다(`tabIndex={-1}` → 낭독기가 제목부터 읽음).
- 운영체제의 '동작 줄이기'(`prefers-reduced-motion: reduce`)를 켠 사용자는 부드러운 스크롤 없이 바로 이동한다. 어지럼을 느끼는 사용자를 위한 접근성 기준이다.
- 모바일 고정 상단 바에 제목이 가리지 않도록 `scroll-margin-top`을 두었다.

**고려한 대안**
- 결과를 버튼 바로 옆(팝업)에 띄우기: 영양소 7개 카드가 들어가기엔 모바일 화면이 좁다.
- 알림 문구만 띄우기: 결과를 보려면 여전히 직접 스크롤해야 한다.

**검증 방법과 결과 (로컬)**
- 390px 브라우저 테스트 2개(동작 줄이기 끔/켬): 제목 포커스, 화면 안, 상단 바에 가리지 않음.
- 수정 전 코드로 되돌리면 포커스 확인에서 실패하는 것을 확인했다.

**예상 질문과 답변**
- Q. 포커스를 왜 옮기나요? 스크롤만 하면 안 되나요?
  A. 눈으로 보는 사용자는 스크롤로 충분하지만, 낭독기 사용자는 포커스가 버튼에 남아 결과가 생긴 걸 모릅니다. 제목에 포커스를 옮기면 결과부터 읽어 줍니다.

## 15. 등산 추가 — 공식 값만, 사용자가 구분할 수 있는 조건만 (2026-11-17)

**문제 상황** 지인 피드백: 운동 기록에 등산이 없다.

**선택한 방법과 이유**
- 2024 Compendium Walking 분류에서 공식 코드·MET를 그대로 가져왔다(17081 3.8, 17082 5.3, 17012 7.8). 값을 만들지 않았다.
- 공식 목록에는 경사도·짐 무게별 항목이 10개 넘게 있지만, 사용자가 "경사 11~20%"를 판단하긴 어렵다. 속도와 배낭 여부만으로 고를 수 있는 3개로 제한했다.
- 확인일을 항목별로 저장할 수 있게 해(`checked_on`), 기존 25개(2026-11-06 확인)와 새 3개(2026-11-17 확인)를 구분했다.

**고려한 대안** 'Climbing hills' 전체 추가: 정확해 보이지만 잘못 고를 가능성이 커져 오히려 오차가 커진다.

**검증 방법과 결과 (로컬)**
- 계산 테스트(70kg·30분: 133 / 185.5 / 273 kcal), 서버 목록 ↔ 화면 이름표 ↔ 체험판 목록 일치 테스트, 브라우저 테스트(분류 8개, 등산 3개, 강도 표시) 통과.

**예상 질문과 답변**
- Q. 목록에 운동을 추가할 때 실수를 어떻게 막나요?
  A. 서버 목록이 기준이고, 화면 이름표와 체험판 목록이 그것과 같은지 테스트가 확인합니다. 하나라도 빠지면 테스트가 실패합니다.
