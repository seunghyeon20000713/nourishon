# 로컬 음식 검색·한 끼 계산 API

구현·검증일: 2026-11-05. 로컬 단일 사용자 개발용입니다. 인증·식사 저장·DB·개인 프로필·추천 기능은 없습니다.

## 실행 환경

FastAPI는 HTTP 요청을 기존 검색·계산 코드에 연결하고, Uvicorn은 서버를 실행합니다.
HTTPX는 FastAPI TestClient의 테스트용 요청 처리에 사용했습니다.
설치 버전과 간접 의존성은 프로젝트 루트 `requirements.txt`에 고정했습니다. `.venv` 자체는 Git에 포함하지 않습니다.

초기 환경에는 pip와 ensurepip가 모두 없었습니다. [PyPA 공식 설치 안내](https://pip.pypa.io/en/stable/installation/)의 get-pip.py로 가상환경에 pip를 준비한 뒤 필요한 패키지만 설치했습니다.
핵심 검증 버전은 FastAPI 0.162.0, Uvicorn 0.54.0, HTTPX 0.28.1입니다.
현재 Starlette는 기존 HTTPX 테스트 연동에 대한 사용 중단 예정 경고를 출력하지만 이번 고정 버전의 테스트는 통과했습니다. 향후 라이브러리 변경 시 호환성을 다시 검증합니다.

pip가 있는 프로젝트 가상환경에서 의존성을 재설치하려면:

```bash
.venv/bin/python -m pip install -r requirements.txt
```

## 서버 시작

먼저 [전체 정제](full-data-normalization.md)를 수행해 `data/processed/mfds-api-full-normalized-20261105/foods.json`과 완료 상태의 `report.json`이 있어야 합니다.
서버는 시작할 때 완료 상태·건수·코드 중복·100g 기준을 확인하고 데이터를 한 번 읽어 메모리에 보관합니다. 데이터가 없거나 잘못되면 시작에 실패합니다.
기본 경로는 현재 정제본의 경로로 고정했습니다. 데이터 버전 선택 설정은 후속 개선 대상입니다.

```bash
.venv/bin/python -B -m uvicorn backend.api:app \
  --host 127.0.0.1 --port 8000 --no-access-log
```

이미 같은 포트에 서버가 실행 중이면 다시 실행하지 않습니다. 직접 터미널에서 시작한 서버는 Ctrl+C로 종료합니다.
외부 접속 주소인 0.0.0.0으로 실행하지 않고 인증 전에는 로컬에서만 사용합니다. 외부 배포는 하지 않았습니다.
공공 API를 다시 호출하거나 `.env`의 공공 API 키를 읽는 서버가 아닙니다.

## 브라우저에서 직접 확인

[Swagger 화면](http://127.0.0.1:8000/docs)에 접속하면 요청을 실행하는 API 설명 화면이 나옵니다. 이후 추가한 사용자용 [로컬 프론트엔드](local-frontend.md)는 5173에서 실행합니다.
Swagger의 JavaScript·스타일은 FastAPI 기본 CDN을 사용하므로 화면 표시에는 해당 자산에 대한 브라우저 접근이 필요합니다.

1. `GET /foods`를 펼치고 `Try it out`을 누릅니다.
2. `q`에 `국밥_콩나물`, `limit`에 20, `offset`에 0을 넣고 `Execute`를 누릅니다.
3. `POST /meals/calculate`에서 아래 가상 섭취 예시를 실행합니다.

```json
{
  "entries": [
    {"food_code": "D101-004160000-0001", "intake_g": 150}
  ]
}
```

해당 예시는 계산 확인용이며 권장 식단이나 사용자 식사 기록이 아닙니다.

## API 계약

| 요청 | 동작 |
|---|---|
| GET /health | 서버 상태, 로드한 식품 수, 로컬 개발 모드 |
| GET /foods?q=검색어&offset=0&limit=20 | 이름 부분 일치 검색. 코드·이름·기준량·출처·기준일·수정일만 반환 |
| POST /meals/calculate | 식품코드·섭취량 목록을 받아 음식별 결과와 7개 성분의 합계·단위·결측 상태 반환 |

검색은 원본 순서와 기존 이름 정규화 규칙을 유지합니다. 검색 결과 전체 건수와 요청한 페이지만 반환하며, limit은 1~100입니다.
한 끼 입력은 1~100개 항목입니다. 섭취량은 0 이상의 유한한 JSON 숫자만 허용하고 숫자 문자열·참/거짓은 거부합니다.
정의되지 않은 입력 필드도 거부합니다. 없는 식품코드는 404, 잘못된 입력은 422입니다.
한 끼 결과의 `known_total`은 확인된 값의 합계이며 결측이 있으면 `partial` 또는 `missing`과 누락 개수를 유지합니다.
전체 식품 목록에서의 행 번호와 생성일·수정일도 계산 결과에 유지합니다.

입력·계산 결과를 파일·DB에 저장하지 않습니다. 요청 검증 오류에 입력 본문을 복사하지 않으며 요청 본문을 별도로 기록하지 않습니다.
실행 명령은 접근 로그도 끄도록 했습니다. 테스트는 가상 데이터만 사용합니다.

## 실제 검증 결과

- `.venv/bin/python -B -m unittest discover -s tests -q` → 기존 52개 + API 8개, 총 60개 통과.
- `pip check` → 의존성 충돌 없음.
- 샌드박스에서는 최소 TestClient도 스레드 시작 중 멈췄습니다. 같은 최소 예제와 전체 테스트를 제한 밖에서 실행해 정상 응답을 확인했습니다. 응용 코드 실패로 오인하지 않도록 구분했습니다.
- 실제 Uvicorn 서버 127.0.0.1:8000에 요청: `/health`에서 식품 수 290,871, `/foods`의 `국밥_콩나물`에서 결과 1개를 확인했습니다.
- 실제 POST 가상 예시: 열량 205.5kcal, 단백질 10.05g.
- `/docs`는 HTTP 200과 Swagger HTML을 확인했습니다. 브라우저 화면의 실제 렌더링을 자동 검사한 것은 아닙니다.
- 빈 검색어 요청은 HTTP 422로 거부했습니다.

## 현재 한계와 다음 단계

검색은 메모리에 로드한 데이터 목록을 순회합니다. 운영용 성능 검증·DB 검색 인덱스·동시 사용자 테스트는 아직 없습니다.
후속 단계에서 React 기반 로컬 화면으로 검색 → 음식 선택 → 섭취량 입력 → 합계를 연결했습니다. 실행과 검증은 [프론트엔드 안내](local-frontend.md)에 있습니다.
실제 식사 저장·인증·프로필과 체성분 정보 등록·개인 목표·추천은 후속 기능입니다.
